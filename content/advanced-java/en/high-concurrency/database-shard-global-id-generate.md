# How to Handle Primary Key IDs?

## Interview question

After database and table sharding, how do you handle the id primary key?

## Interviewer psychology

This is in fact a problem you inevitably face after database and table sharding: how do you generate ids? If, after splitting into multiple tables, each table accumulates from 1, that is certainly not right, and you need a **globally unique** id to support it. So these are all issues you must consider in an actual production environment.

## Answer analysis

### Database-based plans

#### Database auto-increment id

This means that every time your system needs an id, it inserts a row with no business meaning into a table in one database and obtains a database auto-increment id. After getting the id, it writes into the corresponding sharded databases and tables.

The advantage of this plan is that it is convenient and simple, and anyone can use it. The **disadvantage is that the auto-increment id is generated by a single database**, which becomes a bottleneck under high concurrency. If you insist on improving it, you can set up a dedicated service that each time takes the current maximum id, increments a few ids by itself, returns a batch of ids at once, and then updates the current maximum id to the value after incrementing those ids. But **in any case it is based on a single database**.

**Suitable scenarios**: there are only two reasons for database and table sharding, either the concurrency of a single database is too high or the data volume of a single database is too large. Unless your **concurrency is not high but the data volume is too large**, causing the sharding scale-out, you can use this plan, because the maximum concurrency per second may be only a few hundred at most, so a single dedicated database and table can generate the auto-increment primary keys.

#### Setting a database sequence or the step of a table's auto-increment field

You can scale horizontally by setting a database sequence or the step of a table's auto-increment field.

For example, suppose there are now 8 service nodes. Each service node uses a sequence to produce IDs, each sequence has a different starting ID, and they increase in turn, with a step of 8 for all.

![database-id-sequence-step](asset:high-concurrency/database-shard-global-id-generate/database-id-sequence-step.png)

**Suitable scenarios**: when users want to prevent duplicate IDs, this plan is fairly simple to implement and can also meet the performance goal. But the service nodes are fixed and the step is fixed, so it becomes hard to handle if you need to add service nodes in the future.

### UUID

The benefit is that it is generated locally and does not depend on a database. The drawbacks: a UUID is too long and takes up a lot of space, so its **performance as a primary key is too poor**. More importantly, a UUID is not ordered, which causes the B+ tree index to perform too many random writes (continuous IDs can produce some sequential writes). Also, because ordered append operations cannot be produced on writing and an insert operation is needed instead, the whole B+ tree node is read into memory, and after the record is inserted the whole node is written back to disk. When records take up a lot of space, the performance of this operation drops noticeably.

Suitable scenarios: if you want to generate a random file name, serial number or the like, you can use a UUID, but a UUID cannot be used as a primary key.

```java
UUID.randomUUID().toString().replace("-", "") -> sfsdf23423rr234sfdaf
```

### Getting the current system time

This simply gets the current time, but the problem is that **when concurrency is very high**, for example thousands per second, **there will be duplicates**, which is certainly unsuitable. Basically you do not need to consider it.

Suitable scenarios: generally, if this plan is used, the current time is concatenated with many other business fields to form an id. If you find it acceptable in your business, that works too. You can concatenate other business field values with the current time to form a globally unique number.

### The snowflake algorithm

The snowflake algorithm is a distributed id generation algorithm open-sourced by twitter, implemented in Scala. It takes a 64-bit long id, leaves 1 bit unused, and uses 41 bits for the millisecond timestamp, 10 bits for the worker machine id and 12 bits for the sequence number.

-   1 bit: unused. Why? In binary, if the first bit is 1 the number is negative, but the ids we generate are all positive, so the first bit is always 0.
-   41 bits: the timestamp, in milliseconds. 41 bits can represent numbers as large as `2^41 - 1`, that is, it can identify `2^41 - 1` millisecond values, which converts to 69 years.
-   10 bits: records the worker machine id, meaning this service can be deployed on at most 2^10 machines, that is 1024 machines. But of the 10 bits, 5 bits represent the data center id and 5 bits represent the machine id. That means at most `2^5` data centers (32 data centers), and each data center can have `2^5` machines (32 machines).
-   12 bits: records the different ids generated within the same millisecond. The largest number 12 bits can represent is `2^12 - 1 = 4095`, which means this 12-bit number can distinguish 4096 different ids (the numbers 0 to 4095) **within the same millisecond**.

```sh
0 | 0001100 10100010 10111110 10001001 01011100 00 | 10001 | 1 1001 | 0000 00000000
```

```java
public class IdWorker {

    private long workerId;
    private long datacenterId;
    private long sequence;

    public IdWorker(long workerId, long datacenterId, long sequence) {
        // sanity check for workerId
        // this only checks that the data center id and machine id passed in must not exceed 32 and must not be less than 0
        if (workerId > maxWorkerId || workerId < 0) {
            throw new IllegalArgumentException(
                    String.format("worker Id can't be greater than %d or less than 0", maxWorkerId));
        }
        if (datacenterId > maxDatacenterId || datacenterId < 0) {
            throw new IllegalArgumentException(
                    String.format("datacenter Id can't be greater than %d or less than 0", maxDatacenterId));
        }
        System.out.printf(
                "worker starting. timestamp left shift %d, datacenter id bits %d, worker id bits %d, sequence bits %d, workerid %d",
                timestampLeftShift, datacenterIdBits, workerIdBits, sequenceBits, workerId);

        this.workerId = workerId;
        this.datacenterId = datacenterId;
        this.sequence = sequence;
    }

    private long twepoch = 1288834974657L;

    private long workerIdBits = 5L;
    private long datacenterIdBits = 5L;

    // this is a binary operation: 5 bits can hold at most 31 as the largest number, which means the machine id can only be within 32
    private long maxWorkerId = -1L ^ (-1L << workerIdBits);

    // same idea: 5 bits can hold at most 31 as the largest number, and the data center id can only be within 32
    private long maxDatacenterId = -1L ^ (-1L << datacenterIdBits);
    private long sequenceBits = 12L;

    private long workerIdShift = sequenceBits;
    private long datacenterIdShift = sequenceBits + workerIdBits;
    private long timestampLeftShift = sequenceBits + workerIdBits + datacenterIdBits;
    private long sequenceMask = -1L ^ (-1L << sequenceBits);

    private long lastTimestamp = -1L;

    public long getWorkerId() {
        return workerId;
    }

    public long getDatacenterId() {
        return datacenterId;
    }

    public long getTimestamp() {
        return System.currentTimeMillis();
    }

    public synchronized long nextId() {
        // this gets the current timestamp, in milliseconds
        long timestamp = timeGen();

        if (timestamp < lastTimestamp) {
            System.err.printf("clock is moving backwards.  Rejecting requests until %d.", lastTimestamp);
            throw new RuntimeException(String.format(
                    "Clock moved backwards.  Refusing to generate id for %d milliseconds", lastTimestamp - timestamp));
        }

        if (lastTimestamp == timestamp) {
            // this means at most 4096 numbers are allowed within one millisecond
            // whatever you pass in, this bit operation keeps the value within the range of 4096, so a sequence you pass in cannot exceed it
            sequence = (sequence + 1) & sequenceMask;
            if (sequence == 0) {
                timestamp = tilNextMillis(lastTimestamp);
            }
        } else {
            sequence = 0;
        }

        // this records the timestamp of the most recent id generation, in milliseconds
        lastTimestamp = timestamp;

        // here the timestamp is shifted left into the 41-bit part;
        // the data center id is shifted left into its 5-bit part;
        // the machine id is shifted left into its 5-bit part; the sequence number goes in the last 12 bits;
        // finally they are joined into one 64-bit binary number, which in decimal is a long
        return ((timestamp - twepoch) << timestampLeftShift) | (datacenterId << datacenterIdShift)
                | (workerId << workerIdShift) | sequence;
    }

    private long tilNextMillis(long lastTimestamp) {
        long timestamp = timeGen();
        while (timestamp <= lastTimestamp) {
            timestamp = timeGen();
        }
        return timestamp;
    }

    private long timeGen() {
        return System.currentTimeMillis();
    }

    // ---------------test---------------
    public static void main(String[] args) {
        IdWorker worker = new IdWorker(1, 1, 1);
        for (int i = 0; i < 30; i++) {
            System.out.println(worker.nextId());
        }
    }

}

```

How to put it: roughly, the 41 bits are the timestamp in the current millisecond; then 5 bits are the **data center** id you pass in (at most within 32), another 5 bits are the **machine** id you pass in (at most within 32), and the remaining 12 bits are the sequence number: if it is still within the same millisecond as the last id you generated, the sequence is accumulated, up to at most 4096 sequence numbers.

So you use this utility class to build a service yourself, and initialize one such object for every machine in every data center, with the sequence of that machine in that data center initially 0. Then each time a request arrives asking to generate an id for that machine in that data center, you find the corresponding Worker and generate it.

With the snowflake algorithm you can develop your own company's service. As for the data center id and machine id, since 5 bit + 5 bit are reserved for you, you can replace them with other things that carry business meaning.

The snowflake algorithm is relatively reliable, so if you really do distributed id generation, under high concurrency this should give good performance, and in general scenarios with tens of thousands of concurrent requests per second it is also enough for you.
