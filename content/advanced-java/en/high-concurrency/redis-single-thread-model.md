# Differences Between Redis and Memcached

## Interview question

What are the differences between Redis and Memcached? What is the threading model of Redis? Why can single-threaded Redis support high concurrency?

## Interviewer Psychology

This is about the most basic question when asking about Redis. One of the most basic internal principles and characteristics of Redis is that it actually has a **single-threaded working model**. If you do not even know this, how would you know anything when problems arise while using Redis?

The interviewer may also ask about the differences between Redis and Memcached. Memcached was the cache solution commonly used by major internet companies in earlier years, but in recent years it has basically all been Redis, and hardly any company uses Memcached now.

## Answer analysis

### What are the differences between Redis and Memcached?

#### Redis supports complex data structures

Compared with Memcached, Redis has [more data structures](doc:advanced-java/high-concurrency/redis-data-types) and supports richer data operations. If you need a cache that supports more complex structures and operations, Redis is a good choice.

#### Redis natively supports cluster mode

Redis supports cluster mode as of version 3.x, whereas Memcached has no native cluster mode and relies on the client to shard data across the cluster when writing.

#### Performance comparison

Because Redis uses only a **single core** while Memcached can use **multiple cores**, on average Redis performs better than Memcached per core when storing small data. For data above 100k, Memcached performs better than Redis. Although Redis has recently been optimized for storing large data, it is still slightly inferior to Memcached.

### The threading model of Redis

Redis internally uses a file event handler, `file event handler`, which is single-threaded, which is why Redis is called a single-threaded model. It uses an IO multiplexing mechanism to listen to multiple sockets at the same time, puts the sockets that generate events into an in-memory queue, and the event dispatcher selects the corresponding event handler to process each one according to the event type on the socket.

The file event handler consists of 4 parts:

-   multiple sockets
-   the IO multiplexing program
-   the file event dispatcher
-   event handlers (connection acceptance handler, command request handler, command reply handler)

Multiple sockets may generate different operations concurrently, and each operation corresponds to a different file event. But the IO multiplexing program listens to multiple sockets and queues the sockets that generate events. Each time, the event dispatcher takes one socket from the queue and, according to the socket's event type, hands it to the corresponding event handler.

Consider one communication between a client and Redis:

![Redis-single-thread-model](diagram:high-concurrency/redis-single-thread-model/redis-single-thread-model)

Note that communication is done through sockets. If you are not familiar with them, read up on socket network programming first.

First, when the Redis server process initializes, it associates the `AE_READABLE` event of the server socket with the connection acceptance handler.

Client socket01 requests a connection to the server socket of the Redis process. The server socket then generates an `AE_READABLE` event. After the IO multiplexing program detects the event generated by the server socket, it puts that socket into the queue. The file event dispatcher takes the socket from the queue and hands it to the **connection acceptance handler**. The connection acceptance handler creates a socket01 that can communicate with the client, and associates the `AE_READABLE` event of socket01 with the command request handler.

Suppose the client now sends a `set key value` request. The socket01 in Redis generates an `AE_READABLE` event, the IO multiplexing program puts socket01 into the queue, and the event dispatcher takes the `AE_READABLE` event generated by socket01 from the queue. Because the `AE_READABLE` event of socket01 was associated with the command request handler earlier, the event dispatcher hands the event to the command request handler. The command request handler reads the `key value` from socket01 and sets the `key value` in its own memory. After the operation completes, it associates the `AE_WRITABLE` event of socket01 with the command reply handler.

If the client is now ready to receive the result, the socket01 in Redis generates an `AE_WRITABLE` event, which is likewise put into the queue. The event dispatcher finds the associated command reply handler, and the command reply handler writes the result of this operation, such as `ok`, to socket01, after which it removes the association between the `AE_WRITABLE` event of socket01 and the command reply handler.

That completes one communication. For a systematic study of how Redis handles one communication, readers are recommended to read "[Redis Design and Implementation by Huang Jianhong](https://github.com/doocs/technical-books#database)".

### Why is the single-threaded Redis model so efficient?

-   Pure in-memory operations.
-   The core is a non-blocking IO multiplexing mechanism.
-   It is implemented in C. Generally speaking, programs written in C are "closer" to the operating system and run relatively faster.
-   Being single-threaded avoids the frequent context switching of multithreading and prevents the contention problems multithreading may cause.

### Multithreading was introduced starting with Redis 6.0

**Note!** Versions after Redis 6.0 abandoned the single-threaded model design, and **Redis, which originally ran on a single thread, now selectively uses a multithreaded model**.

We just emphasized the efficiency of the single-threaded Redis model, so why introduce multithreading now? This actually shows that in some respects single-threading no longer has an advantage. The Read/Write system calls that read and write the network take up most of the CPU time while Redis executes, so making network reads and writes multithreaded brings a big performance improvement.

**The multithreaded part of Redis is only used to handle network data reads and writes and protocol parsing; command execution is still single-threaded.** It was designed this way so that Redis does not become complicated because of multithreading and need to control concurrency problems with keys, Lua, transactions, LPUSH/LPOP and so on.

### Summary

Redis chose a single-threaded model to handle client requests mainly because the CPU is not the bottleneck of the Redis server, so the performance gain from multithreading cannot offset the development and maintenance costs it brings, and the performance bottleneck of the system is mainly in network I/O. Redis also introduced multithreading for performance reasons: for deleting large key-value pairs, freeing memory with non-blocking multithreading (the free operation does not block network IO reads and writes, because network IO reads and writes and the free command execution are not on the same thread) also reduces the time the Redis main thread is blocked and improves execution efficiency.
